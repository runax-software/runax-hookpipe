# 7. Prerequisite changes in runax-messaging

Part of [Spec: Runax.Hookpipe: runax-messaging core, streaming, library and service](README.md).

| # | Change | Why Hookpipe needs it | Blocks |
| --- | --- | --- | --- |
| **P1** | **Delegate consumers on runtime topics.** Add `bus.AddConsumer(string topic, Func<MessageContext, CancellationToken, ValueTask> handler)`. Internally a `DelegateConsumer : IMessageConsumer`, unversioned, registered as an instance (`ConsumerRegistration` gains an `Instance`). The bus's retry and dead-letter policy apply as for any consumer. | `AddConsumer<T>()` registers a type as a singleton with a compile-time `Topic`. Streams come from YAML, so their topics and count are known only at startup. Calling the transport SPI directly would skip envelope parsing, header merging, and telemetry, and the SPI isn't application API. | Streams (Phase 5) |
| **P2** | **Partition / ordering key.** A reserved header `runax-partition-key` (`MessageHeaders.PartitionKey`) that transports map natively: Kafka record key (today `Message<Null, string>`), Event Hubs partition key, Service Bus session ID, SQS FIFO `MessageGroupId`, Pub/Sub ordering key. Others ignore it. | Parity with v1's Kafka sink, which keys by endpoint ID for per-endpoint ordering | Phase 4 for Kafka users |
| P3 | **Wildcard subscriptions.** Topic patterns where the broker supports them (RabbitMQ `*`/`#`, a Kafka regex subscription), with the dispatcher matching the received topic against the pattern. | Today a RabbitMQ binding of `orders.*` would bind, but `MessageConsumerHostedService` looks up consumers by the exact received routing key, so the messages would be acknowledged and never dispatched. | Nothing. v1 streams list exact topics. |
| P4 | **Batch publish with per-message headers.** For example `PublishBatchAsync<T>(string topic, IReadOnlyList<OutgoingMessage<T>>)`, where `OutgoingMessage<T>` carries the message and its headers. | `IBus.PublishBatchAsync` has no headers parameter, and each envelope needs its own `hookpipe.message.id`. | Nothing. Workers publish one at a time until it lands. |
| P5 | **Broadcast subscription mode.** `bus.SubscriptionMode = Broadcast`: instance-unique Kafka and Redis groups, ephemeral Pub/Sub and Service Bus subscriptions (expiration policy, `AutoDeleteOnIdle`), Redis group cleanup. | Moves [§3.7](architecture.md#37-every-replica-must-see-every-message) from Hookpipe into the library | Nothing. Hookpipe derives group IDs itself. |
| **P6** | **Consumers on an existing bus, added outside its `AddBus` block.** `messaging.AddConsumer(busName, topic, handler)`, reusing P1's delegate consumer. The bus's consumer hosted service must be registered whenever any consumer exists for that bus when the host is built. Today `AddBus` registers it only if its own block added consumers. Adding a consumer to a `PublishOnly` bus fails at startup. | Hookpipe registers every stream subscription this way, on its own buses and on the app's ([§6.1](messaging-integration.md#61-wiring)). In library mode it's the only way, since Hookpipe doesn't control the app's `AddBus` block ([§11.5](packaging.md#115-brokers-in-library-mode)). | Streams (Phase 5) |
| P7 | **Opting a bus out of unkeyed `IBus` resolution.** For example `bus.ExcludeFromDefaultResolution = true`, so the bus is reachable only keyed or through `IBusProvider`. | With no default bus, an unkeyed `IBus` resolves to the only named bus and throws when there are several. Hookpipe's own buses would break an app relying on that. | Nothing. The docs tell such apps to register a default bus or inject it keyed. |

| P8 | **Amazon EventBridge transport**, `Runax.Messaging.Transports.Aws.EventBridge`. Publish-only, through `PutEvents` (10 entries per call). The topic becomes the event's `DetailType`, and the bus name and `Source` come from config. It's on runax-messaging's roadmap. | v1 has an EventBridge sink. As a runax-messaging transport it reaches library users too, instead of living only in the service. | Nothing. The service keeps its own `eventbridge` transport until it ships. |

P1, P2, P6, P7, and P8 are additive, so they're minor-version changes.
